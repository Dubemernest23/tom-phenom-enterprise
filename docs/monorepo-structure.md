# Monorepo & Frontend Architecture Guide

## Repo layout

```
tom-phenom-enterprise/
├── apps/
│   ├── frontend/
│   │   ├── index.html
│   │   ├── src/
│   │   │   ├── main.js              # app entry, router mount

│   │   │   ├── config.js             # API_BASE_URL — generated per environment, see Deploying on Render

│   └── server/                       # built later, by Chidubem — not opencode's job
│       ├── src/
│       │   ├── index.js              # Express app entry
│       │   ├── db.js                 # MySQL connection pool (mysql2)
│       │   ├── routes/                # one file per module — roll-intake.js,
│       │   │                          # packing-bags.js, factory-log.js,
```

This is a Turborepo/Nx-style layout: apps/ groups every runnable
application (frontend, server, and any future apps — e.g. a future admin
tool) so the repo root stays clean, with `docs/` and top-level config
sitting alongside `apps/` rather than mixed in with it.

The `apps/server/` skeleton is for when you build the backend, not
something opencode should generate — opencode's scope is `apps/frontend/`
only.

## Why vanilla JS + Tailwind CSS (no JS framework)

This is a **single-page app (SPA)** — one `index.html`, JS-driven hash
routing between views, never a full page reload as the user moves between
modules. That part hasn't changed.

What has changed from an earlier draft of this doc: styling uses **Tailwind
CSS** utility classes rather than hand-written component CSS, wherever
Tailwind is a natural fit (layout, spacing, typography utilities, states
like hover/focus/disabled). This still doesn't require a JS framework — no
React/Vue/JSX — but it does require a small build step, because Tailwind
needs to scan the markup and generate a CSS file. That's the one place this
app has a build step; everything else stays plain ES modules with no
bundler.

`tailwind.config.js` must extend Tailwind's default theme with the tokens
from `04-design-system.md` (colors, font families, the type scale) rather
than using Tailwind's default palette/fonts — the goal is Tailwind as a
utility engine for *our* design system, not Tailwind's out-of-the-box look
(no default `slate`/`indigo` grays and blues, no default Tailwind font
stack). `tokens.css` still exists and still defines the CSS custom
properties — `tailwind.config.js` should reference those variables (e.g.
`primary: 'var(--color-primary)'`) so there's one source of truth for a
color value, not two.

If page-count or state complexity grows past this, a bundler (Vite) can be
introduced later — Tailwind's CLI build step composes fine with that
transition — but don't reach for it at MVP stage.

## Routing

Hash-based routing (`#/dashboard`, `#/roll-intake`, `#/customers/:id`, etc.)
so the whole thing works as a static SPA with no server-side routing
config needed. `router.js` should:
- Map hash → page module.
- Call that page module's `render(container, params)` function.
- Update the active state on the bottom nav / sidebar to match the current
  route.

## API layer

All backend calls go through `api.js` — one small function per endpoint,
e.g. `getRollIntakes()`, `createRollIntake(data)`, `usePackingBagBatch(id,
data)`. Pages never call `fetch` directly; they call these functions. This
keeps the base URL and error handling in one place, and makes it trivial to
point at a different backend URL (local vs deployed) via a single constant.

```js
// api.js shape
import { API_BASE_URL } from './config.js'; // see "Deploying on Render" for how this gets set per environment

async function request(path, options = {}) { /* fetch + json + error handling, using API_BASE_URL */ }

export const getRollIntakes = () => request('/roll-intake');
export const createRollIntake = (data) => request('/roll-intake', { method: 'POST', body: data });
// ...one pair (or more) per module, matching the endpoints in the schema/PRD docs
```

## State

No global state library needed. `state.js` holds only what's genuinely
shared across pages (e.g. cached KPI totals for the dashboard so navigating
back doesn't always re-fetch). Each page otherwise fetches and owns its own
data on render.

## Build/dev tooling

- No JS bundler required. `index.html` loads `src/main.js` as a module;
  everything else is native ES module imports.
- CSS has one build step: the Tailwind CLI compiles `src/styles/tailwind.css`
  (the `@tailwind` directives, importing `tokens.css`) into
  `src/styles/output.css`, which `index.html` links directly. Run it with
  `npx tailwindcss -i ./src/styles/tailwind.css -o ./src/styles/output.css
  --minify` (add `--watch` for local dev). `output.css` is generated, not
  hand-edited, and not committed.
- If opencode wants a lightweight dev server for live reload on top of the
  Tailwind watch process, that's fine (e.g. any static file server) — but
  the shipped output should still be plain static files plus the compiled
  CSS, not something that requires a Node server to run in production.

## Deploying on Render

Two separate Render services, plus an external database — Render does not
offer managed MySQL, and the decision here is to use an external managed
MySQL host (e.g. Aiven, PlanetScale, or Railway) rather than self-hosting
MySQL on a Render Disk.

**1. Frontend — Render Static Site**
- Root directory: `apps/frontend`
- Build command: `npm install && npx tailwindcss -i ./src/styles/tailwind.css -o ./src/styles/output.css --minify && echo "export const API_BASE_URL = '$API_BASE_URL';" > src/config.js`
- Publish directory: `apps/frontend`

**2. Backend — Render Web Service**
- Root directory: `apps/server`
- Build command: `npm install`
- Start command: `npm start` (should run `node src/index.js`)
- Environment variables (set in the Render dashboard, not committed):
  - `DATABASE_URL` — full connection string from the external MySQL host
  - `PORT` — Render sets this automatically; `src/config/env.js` should read
    `process.env.PORT`, not hardcode it
  - `CORS_ORIGIN` — the frontend's Render static site URL, so Express can
    restrict CORS to it

**Connecting frontend → backend:** since the frontend ships as plain static
files, `process.env` isn't available in the browser. Handle the
local-vs-deployed API URL with a tiny generated config file instead of
hardcoding it in `api.js`:

```js
// frontend/src/config.js — NOT committed with a real value;
// generated by the Render build command from an API_BASE_URL env var,
// or hand-edited locally for dev
export const API_BASE_URL = 'http://localhost:4000/api';
```

On Render, set the Static Site's build command to something like:
```
echo "export const API_BASE_URL = '$API_BASE_URL';" > src/config.js
```
with `API_BASE_URL` set as an environment variable on that service
(pointing at the backend's Render URL, e.g.
`https://tom-phenom-backend.onrender.com/api`). `api.js` then imports
`API_BASE_URL` from `config.js` instead of hardcoding a constant.

**render.yaml (Blueprint, optional but recommended)** — lets both services
be defined in one file at the repo root and stood up together:

```yaml
services:
  - type: web
    name: tom-phenom-backend
    env: node
    rootDir: backend
    buildCommand: npm install
    startCommand: npm start
    envVars:
      - key: DATABASE_URL
        sync: false        # set manually in dashboard — don't commit secrets
      - key: CORS_ORIGIN
        sync: false

  - type: web
    name: tom-phenom-frontend
    env: static
    rootDir: frontend
    buildCommand: npm install && npx tailwindcss -i ./src/styles/tailwind.css -o ./src/styles/output.css --minify && echo "export const API_BASE_URL = '$API_BASE_URL';" > src/config.js
    staticPublishPath: .
    envVars:
      - key: API_BASE_URL
        sync: false
```

**External MySQL:** whichever host you pick (Aiven, PlanetScale, Railway),
the backend only needs one thing from it — a `DATABASE_URL` connection
string set as an env var on the Render web service. `backend/src/db.js`
should read that single value rather than separate host/user/password
fields, so swapping providers later doesn't touch code, only the env var.

## Working with opencode

Point opencode at, in order: `04-design-system.md` (tokens + rules),
`05-frontend-pages-spec.md` (what each page contains), this file (folder
structure + how pages/api/router fit together), then the prompts in
`07-opencode-build-prompts.md`. Build the shared pieces first (tokens.css,
base.css, router, api.js, nav-bar) before any individual page — every page
prompt assumes those exist.
